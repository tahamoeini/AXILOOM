# Jira metadata and guarded mutations

Jira field, project, issue-type, board, and workflow metadata is discovered from the configured source and cached with its source context. Create and edit metadata is requested for the selected project, issue type, and issue. Allowed values and required fields come from that context, not from a static bundled tenant catalog.

The JSON importer can retain field/project/type catalog objects as local evidence. Imported metadata does not establish live permission and is never used as a substitute for current write metadata. Unknown fields remain readable; a required field without a supported value blocks submission rather than guessing.

Jira writes are separate from synchronization and require explicit user action. The current interface checks the relevant Jira permission, fetches the current version before field/status writes, and presents an explicit confirmation for destructive actions. A version check detects observed changes but is not an atomic server-side lock. If a transport failure occurs during a write, refresh the issue before retrying because the remote outcome may be unknown.

The implemented provider path uses Jira REST endpoints compatible with Server/Data Center and bearer personal access tokens over HTTPS. Private network access is the default. Administrators can opt into public IPv4 access only by pinning approved addresses in the workspace profile; DNS answers must match that list, TLS remains verified, and redirects are denied. Read requests retry on rate limits and selected transient failures; writes never retry automatically. A running sync can be cancelled, and errors distinguish authentication, permissions, rate limits, timeouts, and network failures without echoing credential values.

The provider path has not been exercised against a live tenant in this mission. Jira Cloud OAuth is not implemented or supported. Atlassian documents Cloud 3LO as a separate authorization flow through `api.atlassian.com` using an app registered in its developer console and site-specific scopes. App registration, OAuth consent, credential storage/refresh, and a real Cloud site are external gates; DC PAT semantics are not treated as Cloud authentication. Do not infer support from the generic input schema.
